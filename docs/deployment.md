# Deployment and rollback

## Application deployment

Pull requests targeting `main` run `.github/workflows/ci.yml`, which installs
the locked pnpm dependencies, checks formatting, runs type-checking, lint,
tests, and the production build. `.github/workflows/preview.yml` separately
manages the
explicitly named Azure pull-request staging preview and closes it when the
pull request closes.

`.github/workflows/deploy.yml` repeats the release metadata, third-party notice,
type-check, formatting, lint, unit-coverage, build, and asset-budget checks for
approved production candidates, uploads the verified `dist/` artifact once, and
deploys that artifact to Azure Static Web Apps. Pull-request CI additionally
runs the browser/e2e suite. Production deployment is limited to
pushes to `main`, published releases targeting `main`, or a manually approved
run on `main`; the `production` environment supplies the approval gate.
The deploy job is the only application job that receives the production Azure
token. The separate preview workflow uses the `preview` environment and its
`AZURE_STATIC_WEB_APPS_PREVIEW_API_TOKEN` secret.

Every production run writes its result, source ref, and Azure URL (when the
action returns one) to the workflow run summary. The run's deployment job and
the protected `production` environment are the authoritative status records.

The production build creates the PWA manifest and service worker. Do not
commit `dist/`, generated PWA/Workbox output, TypeScript `*.tsbuildinfo` files,
or compiled Vite config files (`vite.config.js` and `vite.config.d.ts`). These
are regenerated by the build and covered by `.gitignore` and `.prettierignore`.

Repository administrators must configure the GitHub `production` environment
with required reviewers and a deployment branch/tag rule limited to approved
production refs (normally `main` and published releases). Store
`AZURE_STATIC_WEB_APPS_API_TOKEN` only in that environment. Configure the
separate `preview` environment with its own
`AZURE_STATIC_WEB_APPS_PREVIEW_API_TOKEN`; never reuse the production token for
pull-request previews.

## Infrastructure deployment

Changes under `infra/` use `.github/workflows/infrastructure.yml`. Every
infrastructure pull request runs formatting, backend-free validation, TFLint,
and Checkov. A pull request from this repository also gets a backend-backed
Terraform plan in the workflow summary and a short-lived plan artifact.

Fork pull requests intentionally do not receive Azure OIDC or Terraform state
access. Their backend-free checks still run. This keeps untrusted pull-request
code outside the state and cloud credential trust boundary; a trusted branch
must produce the plan used for deployment.

For pushes to `main` or a manually dispatched run, the workflow saves one
binary plan, uploads it with the run ID in its name, and waits for the protected
GitHub `production` environment. After approval, the deploy job downloads that
same artifact and applies it by filename. It does not create a second plan.
Required Azure and backend values are provided through GitHub Actions secrets
and OIDC; never add them to the repository.

### Terraform backend bootstrap and recovery

The state storage account is a pre-existing bootstrap dependency and is not
managed by this stack. An infrastructure maintainer creates an Azure resource
group and storage account, enables storage encryption, blob versioning, and a
retention policy, and creates the state container before the first workflow
run. Configure these GitHub secrets: `TF_STATE_RESOURCE_GROUP_NAME`,
`TF_STATE_STORAGE_ACCOUNT_NAME`, `TF_STATE_CONTAINER_NAME`, and
`TF_STATE_KEY`. Configure `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, and
`AZURE_SUBSCRIPTION_ID` for the federated GitHub OIDC identity. The identity
needs least-privilege access to the state container (read, write, and lease
management for locking) and only the resource permissions required by the
Terraform stack.

Set the non-secret repository or environment variables
`TF_RESOURCE_GROUP_NAME`, `TF_RESOURCE_GROUP_LOCATION`, and
`TF_TAG_ENVIRONMENT`; the Terraform configuration has no environment-specific
defaults. Do not put state-account credentials or identifiers in `.tf` files.

To inspect state safely, use a read-only, authenticated `terraform state list`
or `terraform state show` against a copy of the backend configuration. Never
edit the state JSON by hand, disable locking, or delete the state container.
If state is lost or corrupted, stop deployments, preserve the affected blob
versions, and involve the infrastructure maintainers. Restore the newest
known-good blob version to the configured state key, verify the lock and
backend access, run a refresh-free plan for review, and only then approve the
saved plan. If no recoverable version exists, import resources into a new
state only under an approved incident/recovery change; record the incident and
all state operations.

## Rollback

1. Open the latest `02 - App Deploy (Production)` run, record its source ref,
   job status, environment approval, and URL from the run summary, and identify
   the last known-good commit or release.
2. Prefer reverting the offending change on a branch, opening a pull request,
   and merging it through the normal checks. For an urgent application rollback,
   run the workflow manually from `main`, enter the reviewed known-good commit
   SHA in the optional `source_ref` input, and wait for the required
   `production` environment approval. The workflow accepts only a full
   40-character commit SHA, verifies that checkout resolved to that exact
   commit, and requires it to be an ancestor of `main`. This input changes
   only the checked-out build source; it does not bypass validation or
   approval.
3. For an infrastructure regression, revert the Terraform change, run the
   Terraform plan, review the diff and state impact, then approve the protected
   production apply. Do not use the application rollback input for Terraform.
4. Verify the restored URL and run summary, app/PWA loading, the configured
   security headers (including CSP, referrer, and permissions policy),
   microphone permission behavior, and the affected user flow. Record the
   incident and follow-up work in the relevant issue.

Do not delete Terraform state or manually edit Azure resources as a rollback
shortcut. If a rollback could cause data loss or state drift, stop and involve
the infrastructure maintainers before applying it.
